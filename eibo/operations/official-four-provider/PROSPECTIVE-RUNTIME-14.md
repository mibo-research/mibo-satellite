# EIBO-F01 本番向け実行部とオフライン検証

将来の4社観測用に、単一の順序付き実行部、送信直前の制御、L0保存、
一次判定とQCを `prospective_runtime.py` / `prospective_qc.py` に組み込みました。
旧W0・W01の実行経路、凍結済み科学資料、旧証跡は変更していません。
現時点の入口は合成トランスポート専用です。ライブトランスポートを拒否し、
正式日時や運用ロックを作らず、コマンドや予約を追加しません。

## 組み込んだ制御

| 場面 | 実行部の扱い |
|---|---|
| 共通開始点から24時間に到達 | 新規・再試行・メタデータの送信を拒否。試行予約の永続書込後も、トランスポートに渡す直前に再確認 |
| 送信済みで応答を受信 | 元の要求・応答本文とハッシュを保存。目標18時間を超え上限以内なら超過フラグ付き一次、24時間を過ぎた応答は非一次 |
| 応答喪失・通信例外 | 処理済みか不明として該当セルを保留。自動再送せず、確保した費用枠を戻さない。同じ保存先での自動再開も不可 |
| 明示された技術的失敗 | 許可HTTPステータスと既知の技術エラー形式の両方を確認。科学的応答・拒否等は再試行しない。再試行は120秒以上、より長い通知を優先し、Googleの送信開始を65秒以上離す |
| 費用・試行枠 | 各試行前に保守的費用上界と枠を永続予約。未知の費用は送信前に全体停止。総額500 USD、400 USD警告、1セル最大2試行、追加再試行70／社・280／全体、POST 770／社・3,080／全体、GET 3／社・12／全体、HTTP合計3,092 |

金額の単位は整数の百万分の1 USDです。応答欠落・不明費用・失敗を無料とせず、
この実装では試行終了後も予約を解放しません。費用上界が供給されることが前提で、
今回の合成値は実価格・請求額の見積りではありません。時刻の逆行を検知した場合も
以後の送信を保留し、受信済み本文は保存します。

## 検証方法と範囲

[見直した配置](OFFLINE-CAPACITY-13-RESULT.md)の合成スケジュールから、4社・2,800件・10反復を
そのまま読み込み、同じ1試行1秒の直列模擬条件を使用します。
一件ずつトランスポートに渡し、送信順と要求・応答ハッシュを比較します。
障害シナリオでは締切境界、遅着、応答喪失、技術再試行、費用・試行枠を同じ実行部で検査し、
原本の改変・不整合は別の読取専用QCで検出します。

**結果：4社各700件、全2,800件が17時間16分4.651秒で完了。** 18時間まで43分55.349秒、
Googleの最短開始間隔は65秒、全件の要求・応答ハッシュが前回と一致し、QCは合格でした。
拒否等を含め通常の全件シナリオで再試行はゼロです。
別記録の12障害ケースも通過しました。締切時に送信ゼロ、締切後の応答は保存して非一次、
応答喪失のセルに第2試行なし、確認済み429で長い通知を採用、未知の費用上界で全件送信前停止、
500 USDに達した後の追加送信なし、4件目のメタデータ要求を拒否、などを確認しました。
追加テストで、費用予約の書込中に締切をまたいだ場合、時刻逆行、上限各種、認証文字列の
非保存・非ハッシュ化、証跡改変の検出も確認しています。

再現はモジュールの開発環境から `python tests/offline_capacity14.py NEW_OUTPUT_DIRECTORY --compare-to RETIMED_RUN_DIRECTORY`。
既存アーカイブは上書きしません。正式実行には、実料金の保守的上界（M05の内部検索等を含む）、
正式用profile・運用ロック・許可、実アカウント・実環境の確認が別途必要です。
未確認の利用条件・機関判断はそのまま残し、追加資料は求めません。
最終検証の証跡は外部永続領域の `preparations/EIBO-4P-SOLO-001/offline-capacity/run-04/` の
`report.json` と `archive-checksums.json`。全データは非公式です。
予約・provider API送信・xAI・W01の実行はゼロです。
